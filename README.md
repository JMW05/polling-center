# Polling Center

Polling Center is a shared, multi-tenant polling web app built for Jana's
organizations (TCABC — Tougaloo College Athletic Booster Club, TCRDF —
Tougaloo College Research and Development Foundation, and others). One
deployment serves multiple organizations, each with its own admins,
members, and polls, cleanly isolated from one another.

## Supported poll types

- **Meeting availability** — propose a set of date/time slots (shown in
  the poll's own configured timezone, never the browser's) and collect
  respondent availability across them.
- **Choice / decision** — single- or multi-select voting on a set of
  options, with an optional "secret ballot" mode (see below).
- **Election** — always a secret ballot, access-gated by per-voter tokens
  generated by an org admin, with results kept hidden until the
  configured release rule allows it.
- **Survey / feedback** — an ordered set of questions (single/multi
  choice, yes/no, rating scale, free text).

Every poll type shares a common settings surface: who can respond (open
link, one-per-device, requires name & email, or voter-code/secret-ballot
token), timezone, open/close times, whether respondents can change their
answer before close, results visibility (hidden / after you respond /
while open / after close / released manually), and whether respondent
identities are shown alongside results.

## Architecture

- **Frontend**: plain static files — `index.html` (page shell), `css/`
  and `js/` (native ES modules loaded with `<script type="module">`). No
  build step, no bundler, no framework dependency beyond the Supabase JS
  client loaded from a CDN. This is deliberate: the repository root is
  served as-is. See `docs/phase1-implementation-map.md` §1 for the module
  layout.
- **Backend**: [Supabase](https://supabase.com) — Postgres, Row Level
  Security, and a set of `SECURITY DEFINER` RPC functions that are the
  *only* write path for poll structure and voting. See
  [`docs/architecture.md`](docs/architecture.md) for the full data model,
  the RPC surface, and how anonymity/election-secrecy is enforced at the
  database layer rather than trusted to the frontend.
- **Hosting target**: [Cloudflare Pages](https://pages.cloudflare.com/)
  (or equivalent static Cloudflare hosting), serving `index.html` at
  **`https://polls.wwjanado.com`**. See
  [`docs/deployment.md`](docs/deployment.md) for the full setup,
  including the Supabase Auth URL configuration this domain requires.

This project intentionally does **not** use Netlify going forward — see
`CLAUDE.md` for why, and `docs/deployment.md` for the Cloudflare setup
that replaces it.

## Running / testing locally

There's no build step. To work on the frontend:

```bash
# from the repository root
python3 -m http.server 8080
# then open http://localhost:8080/index.html
```

Any static file server works equally well (`npx serve`, VS Code's Live
Server, etc.) — the only requirement is serving the repository root over HTTP
(not `file://`), since browsers refuse to load ES modules from `file://`, and the Supabase JS client and the page's own
`fetch`/`hashchange` routing expect a real origin.

The frontend talks directly to the existing Supabase project (URL and
anon/publishable key are embedded in `js/supabase-client.js` — the anon key is
designed to be public and is protected by Row Level Security, so this is
expected and safe). There is no local/mocked backend; testing against the
real Supabase project's real RLS policies and RPCs is the point — see
`docs/QA.md` for the current QA status and what's still pending real
browser verification.

To sanity-check the frontend's JavaScript syntax before committing:

```bash
for f in $(find js -name '*.js'); do node --input-type=module --check < "$f" || echo "FAILED: $f"; done
```
